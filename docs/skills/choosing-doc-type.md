# choosing-doc-type

문서를 쓰기 **전에** 유형부터 정한다. Diátaxis의 4유형(학습 · 문제 해결 · 참조 · 설명) 중 하나를 고르고, 그 유형의 규칙으로만 쓴다. 한 문서에 한 유형만 둔다. 두 유형이 필요하면 문서를 나누고 서로 링크한다.

## 언제 쓰나

- **"문서 하나로 정리해줘"를 받았을 때.** 목차를 잡기 전에 먼저 부른다.
- **인수인계 · 온보딩 문서.** "다 넣어 주자"로 시작해 설명 · 절차 · 설정 목록이 한 문서에 뒤섞이기 쉬운 문서다.
- **README가 길어져서 읽히지 않을 때.** 어디서 잘라 낼지 판단 근거가 필요하다.

## 이렇게 부른다

```
다음 주에 신입 들어오는데, 습관 기록 웹 레포 문서 하나로 정리해줘
```
```
배포 가이드 쓰려고 하는데 어떤 식으로 써야 할까
```

## 결과 예시

두 질문으로 판정한다. 독자는 **배우러** 왔는가, **일하다가** 왔는가? 원하는 것은 **실행**인가, **이해**인가?

|  | 실행하려 한다 | 이해하려 한다 |
| --- | --- | --- |
| 배우는 중 | 학습(튜토리얼) | 설명 |
| 일하는 중 | 문제 해결(how-to) | 참조 |

위 첫 요청에 대한 답:

```
유형 판정: 주 문서는 학습(튜토리얼)입니다.
근거 — 독자는 신입(배우는 중)이고, 첫 주 목표는 로컬에서 앱을 띄워 기록 화면을 고쳐 보는 것(실행)입니다.

문서 세트
1. [주] 첫날 튜토리얼: 로컬에서 습관 기록 웹 띄우고 기록 카드 문구 하나 바꿔 보기
2. [분리 권장 · 설명] 구조와 결정 이유: 왜 웹·앱이 API 패키지를 공유하는지
3. [분리 권장 · 참조] 환경 변수 목록: 이름 · 기본값 · 필수 여부 표

"왜 이렇게 만들었나"를 튜토리얼 중간에 넣지 않고 2번으로 링크합니다.
```

## 쓰지 않는 경우

- 유형이 이미 정해진 문서를 이어 쓰거나 고칠 때
- 목차가 나온 뒤의 구조 진단: [doc-structure-review](doc-structure-review.md)

이 스킬부터 문장 윤문까지 이어지는 흐름은 [문서 하나를 끝까지](../scenarios/doc-pipeline.md)에 있다.
