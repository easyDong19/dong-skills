# doc-sentence-polish

기술 문서의 문장 · 문단을 6개 원칙으로 진단하고, **하나의 통합 수정안**을 낸다. 의미는 바꾸지 않고 표현만 고친다. 피드백만 내고 파일은 직접 고치지 않는다.

1. 필요한 정보만 남기기 (한 문장 한 생각)
2. 메타 담화 줄이기 ("앞서 설명했듯이")
3. 구체적으로 쓰기
4. 일관되게 쓰기 (용어 통일)
5. 문장의 주체를 분명하게 (수동형 → 능동형)
6. 직역 용어 대신 실무 용어 쓰기 (되돌리기 → 롤백, 결과물 → 빌드 산출물)

## 언제 쓰나

- **README · 가이드 · 스펙 문장이 어색할 때.** "번역투 같다", "읽기 힘들다"는 말을 들었을 때.
- **비개발자도 읽는 문서.** 실무 용어는 그대로 두고 첫 등장에 뜻을 덧붙이는 방향으로 고친다.
- 구조는 괜찮은데 문장 단위로 다듬고 싶을 때.

## 이렇게 부른다

```
이 문단 좀 다듬어줘. 번역투 같아
```
```
배포 가이드 문장 리뷰해줘
```

## 결과 예시

입력:

> 앞서 설명했듯이, 배포는 main 브랜치에 머지가 되면 자동으로 진행되게 되며 문제가 생기면 표지판을 직전 자리로 되돌리면 됩니다. 환경 변수는 결과물에 박히기 때문에 값을 바꾼 뒤에는 빌드가 다시 되어야 합니다.

출력:

```
1. 원칙별 문제
- 원칙 1: 첫 문장에 "배포 조건"과 "문제 시 대응" 두 생각이 섞임
- 원칙 2: "앞서 설명했듯이"는 정보가 없는 메타 담화
- 원칙 5: "진행되게 되며", "빌드가 다시 되어야" — 주체가 흐린 피동
- 원칙 6: "표지판을 직전 자리로 되돌리면" → 롤백, "결과물에 박히기" → 빌드 산출물에 포함

2. 최종 수정안
main 브랜치에 머지하면 자동으로 배포됩니다. 문제가 생기면 배포 브랜치를
직전 배포 커밋으로 롤백하세요. 환경 변수는 빌드 산출물에 포함되므로,
값을 바꾼 뒤에는 다시 빌드하세요.

3. 한 줄 요약
두 생각을 문장으로 나누고, 피동을 능동으로, 직역 조어를 실무 용어로 바꿨습니다.
```
