# doc-structure-review

기술 문서의 **목차와 정보 구조**를 5개 원칙으로 진단하고, 개선안을 **하나의 통합 목차**로 낸다. 문장은 고치지 않는다.

| # | 원칙 | 보는 것 |
| --- | --- | --- |
| 1 | 한 페이지 하나의 목표 | `####` 이상 중첩, 개념 과다 |
| 2 | 개요 빠뜨리지 않기 | 첫머리에 "읽으면 무엇을 얻는가" |
| 3 | 예측 가능한 구조 | 같은 수준 제목의 패턴 · 용어 일관성 |
| 4 | 가치를 먼저 | 이점이 도입부에, 세부 설정은 뒤에 |
| 5 | 효과적인 제목 | 키워드 포함 · 30자 이내 · 의문문 지양 |

## 언제 쓰나

- **초안 목차가 나온 뒤.** 본문을 채우기 전에 구조부터 바로잡는다.
- **"이 문서 어떻게 나눌까"** 고민될 때.
- 리뷰에서 "읽기 어렵다"는 말만 듣고 이유를 모를 때.

## 이렇게 부른다

```
이 README 목차 구조 좀 봐줘
```
```
문서가 너무 길어진 것 같은데 페이지를 어떻게 나누면 좋을지 피드백해줘
```

## 결과 예시

입력 (습관 기록 웹 README 초안 목차):

```
# 습관 기록 웹
## 아키텍처
## 왜 Next.js를 썼나요?
## 설치
### Node 버전
#### nvm 사용 시
#### volta 사용 시
## 환경 변수
## 배포는 어떻게 하나요?
## 트러블슈팅
```

출력 (요약):

```
독자·목표: 주어지지 않아 초안에서 추론함 — 처음 레포를 받은 개발자가 로컬 실행까지 가는 것.

1. 원칙별 진단
- 원칙 1 (문제): "설치 > Node 버전 > nvm 사용 시"가 4단계 중첩. 설치 문서 안에 버전 관리자 안내까지 들어 있음
- 원칙 2 (문제): 개요 없이 "아키텍처"로 시작. 이 레포가 무엇인지 첫 화면에서 알 수 없음
- 원칙 3 (문제): "설치"(명사) / "배포는 어떻게 하나요?"(의문문) 제목 패턴 혼재
- 원칙 4 (문제): 로컬 실행이라는 독자 목표보다 아키텍처·기술 선택 이유가 앞에 있음
- 원칙 5 (문제): 의문문 제목 2개

2. 최종 개선안
# 습관 기록 웹
(개요 2~3문장: 무엇인지 · 이 문서로 무엇을 할 수 있는지)
## 로컬에서 실행하기
- 요구 사항 (Node 22)
- 설치와 실행
## 환경 변수
## 배포
## 문제 해결
## 더 읽을거리
- 구조와 기술 선택 이유 → docs/architecture.md (분리)
- Node 버전 관리자 설정 → docs/node-version.md (분리)

3. 변경 이유
- 아키텍처·Next.js 선택 이유를 별도 문서로: 원칙 1·4
- nvm/volta 안내 분리, 중첩 2단계로: 원칙 1
- 의문문 제목을 명사형으로: 원칙 3·5
```

## 쓰지 않는 경우

- 문장 표현 다듬기: [doc-sentence-polish](doc-sentence-polish.md)
- 아직 유형도 안 정한 문서: [choosing-doc-type](choosing-doc-type.md)부터
