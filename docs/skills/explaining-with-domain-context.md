# explaining-with-domain-context

코드 · 기능 · 플로우 · 설계 결정을 **문제와 도메인부터** 설명한다. 단계를 나열하지 않고, "무엇이 이 단계를 촉발하고, 이 단계가 없으면 무엇이 무너지는가"로 잇는다. 독자는 이 저장소도 도메인도 모른다고 가정한다.

설명은 이 순서로 짠다.

1. 문제와 도메인 (도메인 용어는 첫 등장에 한 줄 정의)
2. 큰 그림 (이 조각의 위치와 경계)
3. 플로우 — 인과의 사슬로
4. 의사결정과 기각된 대안
5. 함정과 제약
6. 근거 링크 (`path:line`, 커밋, 이슈)

## 언제 쓰나

- **"이거 어떻게 동작해?"** 같은 캐주얼한 질문에도. 처음 인수인계받는 사람에게 말하듯 답한다.
- **인수인계 · 온보딩 문서의 본문.** 유형은 [choosing-doc-type](choosing-doc-type.md)에서 "설명"으로 정해진 문서.
- **PR 설명 · 이슈 배경.** "왜 이렇게 바꿨나"를 기각된 대안과 함께 남길 때.

## 이렇게 부른다

```
연속 달성 일수 계산 어떻게 동작하는지 설명해줘
```
```
이 PR 왜 이렇게 바꿨는지 인수인계용으로 정리해줘
```

## 결과 예시

첫 요청에 대한 답의 앞부분 (가상 "습관 기록" 앱 기준, 경로도 가상):

> **연속 달성(streak, 하루도 빠지지 않고 습관을 체크한 날 수)** 은 사용자가 앱을 계속 여는 가장 큰 이유다. 그래서 숫자가 하루라도 틀리면 바로 문의가 들어온다. 실제로 가장 많이 틀린 곳은 "하루"의 경계였다.
>
> 계산은 앱이 아니라 API 서버에서 한다. 앱은 체크 시각만 보내고, 서버가 그 시각을 **사용자의 시간대로 바꿔 날짜를 정한 뒤** 연속 일수를 다시 센다(`apps/api/src/streak/compute.ts:42`). 시간대를 바꾸지 않고 서버 시각(UTC)으로 날짜를 자르면, 한국 사용자가 오전 8시 전에 체크한 기록이 전날로 들어가 연속 기록이 끊긴 것처럼 보인다.
>
> 원래는 앱에서 계산했다. 기기 시계를 바꾸면 연속 기록을 조작할 수 있었고, 웹과 앱이 서로 다른 숫자를 보여 줬기 때문에 서버로 옮겼다(커밋 `3f2a91c`). 서버에 매일 밤 일괄 계산을 돌리는 방법도 검토했지만, 체크 직후 숫자가 바로 바뀌지 않아 기각했다.
>
> **함정:** 사용자가 설정에서 시간대를 바꾸면 과거 기록의 날짜도 다시 계산된다. 이 재계산을 끄면 해외 출장 중인 사용자의 기록이 끊긴다.

파일 목록이나 "등장 인물" 표로 시작하지 않는다. 표와 다이어그램은 서사가 끝난 뒤에 보조로 붙인다.
