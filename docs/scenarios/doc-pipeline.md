# 문서 하나를 끝까지: 유형 결정 → 구조 리뷰 → 문장 윤문

신입 온보딩용으로 "습관 기록 웹" 레포 문서를 새로 쓰는 상황을 예로, 문서 스킬 네 개를 순서대로 쓰는 방법이다. 각 단계는 앞 단계의 결과물을 입력으로 받는다.

## 1. 유형 정하기: choosing-doc-type

목차를 잡기 전에 유형부터 정한다.

```
다음 주에 신입 들어오는데, 습관 기록 웹 레포 문서 하나로 정리해줘
```

결과: 주 문서는 **학습(튜토리얼)**. "구조와 결정 이유"(설명)와 "환경 변수 목록"(참조)은 별도 문서로 분리를 권한다. → [판정 예시](../skills/choosing-doc-type.md#결과-예시)

여기서 문서 세트가 정해진다. 아래 단계는 문서마다 따로 돈다.

## 2. 설명 문서 본문 쓰기: explaining-with-domain-context

분리한 "구조와 결정 이유" 문서는 설명 유형이다. 본문을 이 스킬로 쓴다.

```
웹·앱이 API 패키지를 공유하는 구조, 인수인계 문서용으로 설명해줘
```

문제와 도메인 → 큰 그림 → 인과로 잇는 플로우 → 기각된 대안 → 함정 순서로 나온다. → [설명 예시](../skills/explaining-with-domain-context.md#결과-예시)

튜토리얼 · 참조 문서는 이 단계를 건너뛰고 유형별 체크리스트대로 직접 쓴다.

## 3. 목차 점검: doc-structure-review

초안이 나오면 문장을 다듬기 전에 구조부터 본다. 구조가 바뀌면 다듬은 문장이 버려지기 때문이다.

```
이 README 목차 구조 좀 봐줘
```

5개 원칙별 진단과 **통합 개선 목차 하나**가 나온다. 페이지를 더 나눠야 하면 여기서 나눈다. → [구조 리뷰 예시](../skills/doc-structure-review.md#결과-예시)

## 4. 문장 다듬기: doc-sentence-polish

구조가 확정된 뒤 문단 단위로 다듬는다.

```
설치·배포 절 문장 리뷰해줘
```

6개 원칙 중 걸리는 항목만 짚고, 수정안 하나를 낸다. 의미는 바꾸지 않는다. → [윤문 예시](../skills/doc-sentence-polish.md#결과-예시)

## 순서를 지키는 이유

| 순서를 바꾸면 | 생기는 일 |
| --- | --- |
| 유형 결정 없이 목차부터 | 설명 · 절차 · 설정 표가 한 문서에 섞이고, 구조 리뷰가 "전부 나눠라"로 끝난다 |
| 구조 리뷰 전에 윤문 | 다듬은 문단이 다른 문서로 옮겨지거나 지워진다 |
| 윤문하면서 구조도 고침 | 두 종류의 피드백이 섞여 무엇을 왜 바꿨는지 추적하기 어렵다 |
