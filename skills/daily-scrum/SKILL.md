# Daily Scrum

스크럼에서 30초 안에 읽는 메모. **읽는 사람 중 누군가는 코드를 모른다** — 기획·디자인·
경영 등 비개발 직군이 같은 테이블을 본다. 그래서 항목은 "무슨 코드를 만졌나"가 아니라
**"어느 제품의 무슨 기능이 어떻게 됐나"**다.

## Output contract

스크럼 테이블(노션 등)의 **'오늘 한 일' 셀 하나**에 붙일 평문을 만든다.
('내일 할 일'·'질문·블로커' 칸은 이 스킬이 만들지 않는다. 요청받으면 그때 쓴다.)

셀은 마크다운을 렌더하지 않는다. `**볼드**`·`- ` 불릿·`#` 헤더를 쓰면 문자 그대로 보이므로
쓰지 않는다. `•`(1단계)와 `◦`(2단계) 문자와 줄바꿈만 쓴다.

**전체를 하나의 ``` 코드블록으로 감싸 제시한다** — 사용자가 셀에 깔끔히 복사하도록.
(코드블록의 백틱은 붙지 않고 안의 평문만 복사된다.)

구성:

1. **제품 이름 한 줄** — 그날 만진 제품·과제마다 하나. 평문이고 볼드를 쓰지 않는다.
2. 그 아래 **기능 불릿** — `• `로 시작. 한 화면 안의 여러 기능은 `    ◦ `로 한 단계 내린다.
3. **맨 아래 `참조` 줄** — 그날의 PR URL을 모아 적는다. 없으면 줄째 생략.
   사람이 열어볼 링크(QA 리포트·분석 아티팩트)는 여기가 아니라 **해당 항목 아래**에 붙인다.

제품이 여러 개면 제품 블록 사이를 빈 줄로 띄운다. 중첩은 **2단계까지**.

출력 예시 (이 코드블록째 사용자에게 제시한다):

```
습관 기록 (웹)
• 오늘 기록 카드를 누르면 상세 화면으로 넘어가게 함
• 로그아웃 후 다른 계정으로 들어가도 앞 사람 데이터가 보이던 문제 해결
• 프로필 사진 업로드
    ◦ 저장되는 파일 이름에서 내부 관리번호를 빼 사람이 읽을 수 있게 함

습관 기록 (앱)
• 기록 필터 화면 만들기
    ◦ 화면 캡처: https://claude.ai/artifact/<그날 만든 QA 리포트>

참조
https://github.com/<owner>/<repo>/pull/165
https://github.com/<owner>/<repo>/pull/159
```

**출력에 줄표(`—`·`–`)를 쓰지 않는다.** "작업 — 효과"처럼 줄표로 잇는 건 AI가 쓴 티가
가장 먼저 나는 표식이다. 쉼표로 잇거나(`…정리, 앱에서 그대로 재사용`), 문장을 나누거나,
`◦` 한 줄로 내린다. 기본 모드·자세히 모드 모두 해당한다. 출력 직전에 `—`가 남았는지 훑는다.

이 계약에 없는 것은 출력에 없다: 날짜 헤더(노션 행이 이미 날짜를 갖는다), 레포 약칭(`fe`·`mobile`),
마크다운 볼드·헤더·`- ` 불릿, `**문제:**`/`**조치:**` 같은 라벨, 검증 결과 나열, 파일 경로 목록,
서문("정리했습니다")·맺음말.

**여러 컬럼으로 나눠 달라고 하면**(작업 / PR / 효과 등) 각 항목을 그 컬럼 값으로 쪼개 제시한다 —
한 줄에 묶지 말고 컬럼별 셀 값으로.

### 제품 이름 짓기

레포 이름이 아니라 **사람들이 부르는 제품·과제 이름**을 쓴다. 한 제품이 웹·앱으로 갈리면
괄호로 플랫폼을 붙인다.

| 이렇게 쓰지 않는다 | 이렇게 쓴다 |
|---|---|
| `fe`, `mobile`, `apps/web` | `습관 기록 (웹)`, `습관 기록 (앱)` |
| `habit-tracker-monorepo` | `습관 기록` |
| `packages/api` | 그 변경이 닿는 제품 이름으로 적는다 (`습관 기록 (웹·앱 공통)`) |

### 참조 줄

PR URL은 **사용자 본인이 나중에 되짚기 위한 것**이다. 본문 불릿에는 `(#66)`·`fe#54` 같은
번호 표기를 섞지 않는다 — 비개발 독자에게 아무 의미가 없고 문장만 끊는다. 맨 아래
`참조` 줄 뒤에 **한 줄에 하나씩** 전체 URL로 모은다. 한 줄에 여러 개를 이으면 셀에서
줄이 넘쳐 안 읽힌다.

```bash
gh pr list --author "@me" --state all --limit 10 --json number,title,url,updatedAt
```

### 볼 수 있는 링크는 항목 아래에

**비개발 독자가 열어서 결과를 눈으로 볼 수 있는 링크는 `참조` 줄로 내리지 않는다.**
`참조`는 본인이 나중에 되짚는 용도라 아무도 안 누른다. 그런 링크는 해당 항목 바로 아래
`    ◦ <무엇인지>: <URL>` 로 붙여 읽는 흐름 안에 둔다.

| 이런 링크 | 어디에 |
|---|---|
| QA 리포트, 뷰 리뷰 캡처 | 그 화면 항목 아래 `◦` (`◦ 화면 캡처: …`) |
| 비교·분석 아티팩트, 대시보드 | 그 작업 항목 아래 `◦` (`◦ 정리 전후 비교: …`) |
| 기획서·디자인 시안 | 그 작업 항목 아래 `◦` |
| PR·커밋 | 맨 아래 `참조` 줄 |

이 스킬이 돌기 전에 만든 아티팩트를 찾으려면 Artifact 도구의 `list`를 쓴다 — 제목과
갱신일로 그날 작업과 짝지어진다. 한 항목에 링크가 둘 이상이면 각각 `◦` 한 줄씩.

## 기능 이름으로 쓴다

**항목의 주어는 화면·버튼·기능이지 모듈·라이브러리·패턴이 아니다.**
읽는 사람이 제품을 써 보면 알 수 있는 말로 쓴다.

| 쓰지 않는다 | 이렇게 쓴다 |
|---|---|
| React Query 캐시 폐기 일원화 | 로그아웃하면 앞 계정 데이터가 남아 보이던 문제 해결 |
| 쿼리키 정리 / 캐시 무효화 | 화면을 다시 열었을 때 옛 정보가 보이던 문제 해결 |
| zod 스키마 검증 추가 | 잘못된 값이 들어오면 저장 전에 걸러냄 |
| reducer로 상태 구현 | 회원가입 화면을 단계별로 넘어가게 만듦 |
| 컴포넌트 공용화 / 파편화 해소 | 같은 버튼을 화면마다 다시 만들지 않게 정리 |
| FSD 경계 위반 수정 | (이 줄 자체를 쓰지 않는다 — 읽는 사람에게 사건이 아니다) |

약어·영문 라이브러리 이름이 꼭 필요하면 **괄호로 풀어 준다**: "영상 실시간 재생(HLS)",
"그림 그리는 도구(Konva)". 풀어 줄 수 없으면 그 항목을 버린다.

## 순수 내부 작업은 "그래서 무엇이 가능해졌나"로

리팩토링·CI·테스트·설정 변경은 화면이 안 변한다. *무엇을 했나*가 아니라
**그 결과 무엇이 가능해졌나**를 쓴다.

- ❌ 웹·모바일 공용 정책 코드 shim 제거, 순 −423줄
- ✅ 알림 버튼 노출 규칙을 웹·앱이 같은 자리에서 가져다 쓰게 정리, 앱에 같은 화면 만들 때 그대로 재사용

바꿔 쓸 말이 없으면(빌드 설정 손봄, 의존성 버전 올림 등) **그 항목은 버린다.** 스크럼 메모는
그날의 전부를 담는 장부가 아니다. 단, 그 작업이 하루의 대부분이었다면 한 줄로 남긴다:
"개발 환경 정비(다른 기능 작업 없음)".

## 항목을 만드는 단위

**커밋 1개 = 항목 1개가 아니다. 사람이 인식하는 작업 1개 = 항목 1개다.**
한 PR/브랜치의 커밋 5개는 불릿 1개로 합친다. `feat` → `test` → `refactor` 로 쪼갠 건 과정이지 항목이 아니다.

**커밋 제목을 그대로 붙여넣지 않는다.** 커밋 제목은 개발자에게 쓴 말이다. 위 치환표를 거친다.

한 화면에 대해 여러 기능을 붙였으면 화면을 `•`로 올리고 기능을 `◦`로 내린다.

## 수집 (출력 전에 실행)

```bash
git log --since="yesterday 23:59" --pretty=format:"%h %ad %s" --date=format:"%m-%d %H:%M" --all
```

- `--all`을 빼지 말 것. 오늘 작업이 머지 전 브랜치에만 있는 경우가 흔하다.
- **레포 하나만 보고 끝내지 않는다.** 하루에 제품 두셋을 오가는 게 흔하다. 사용자가 어느
  제품들을 만졌는지 모르면 물어보고, 각 레포에서 같은 명령을 돌린다.
- 코드 변경 없이 문서만 쓴 것도 항목이다. 조사/디버깅만 하고 커밋이 없어도 항목이다.
  회의·기획도 항목이다("사이드 프로젝트 · 정기 회의").
- **그날 만든 아티팩트를 Artifact `list`로 확인한다.** 화면 작업이면 QA 리포트·뷰 리뷰가,
  문서·조사 작업이면 분석 아티팩트가 거의 항상 딸려 있다. 위 "볼 수 있는 링크는 항목 아래에".
- 날짜는 사용자 로컬 시간대 기준. "어제"를 물으면 범위를 하루 당긴다.

### 제품·화면 이름 역추적

커밋 메시지에는 제품 이름도 화면 이름도 잘 안 나온다. 불릿을 쓰기 전에 한 단계 더 본다:

- **바뀐 파일 경로 → 화면 이름.** 라우트 파일(`app/…`·`pages/…`)과 `widgets/`·`features/`
  디렉토리 이름이 화면을 알려준다. `git show --stat <sha>`로 본다.
- **레포·워크스페이스 → 제품 이름.** 위 "제품 이름 짓기" 표.
- 그래도 무슨 화면인지 모르겠으면 **추측해서 쓰지 말고 사용자에게 묻는다.**

## 길이 조절

- **더 짧게**: 2단계 `◦` 중첩을 걷고 `•` 한 단계만 남긴다. (제품 이름 줄·평문·코드블록은 유지)
- 기본: 위 Output contract.
- **자세히**: 아래 Detailed mode로 전환한다. **단 Detailed mode는 마크다운 문서용이라
  테이블 셀 대상이 아니다** — docs·위클리·공유 채널에 붙일 때만 쓴다. 사용자가 셀에 붙일
  거라고 하면 자세히 요청이어도 평문 형식을 유지하되 항목 설명만 길게 쓴다.

## Detailed mode

사용자가 "자세히", "풀어서", "배경까지", "근거도", "왜 했는지도"를 요청하거나, 위클리·공유
채널에 붙일 **설명형 문서**를 원하면 계약이 바뀐다. 기본 모드와 마찬가지로 읽는 사람이 이
도메인을 모른다고 가정하되, **배경과 검증까지 덧붙인다.**
(경영진·의사결정권자용 개조식 보고서는 이 스킬의 범위가 아니다.)

### 구조 — 배경 → 작업 → 검증

```markdown
# <무엇이 좋아졌는지가 드러나는 작업 제목> (PR #NN)

**배경**: <이 작업이 왜 필요했는지를 모르는 사람 기준으로 풀어서. 관련 도메인
규칙·이전 작업 맥락을 여기서 다 깔아준다. 2~4문장>

**이번 작업**

- <무엇을 어떻게 바꿨는지> (<규모·근거>)
- 효과: <그래서 무엇이 좋아졌는가. 다음 작업과의 연결까지>

**<부수 섹션 (있으면)>**

- <발견한 문제와 메커니즘> → <조치>

**검증**: <핵심 수치 한 줄> · [PR #NN](url)
```

- 섹션 제목은 `**볼드**` 인라인. `##` 소제목·표·3단계 중첩을 쓰지 않는다.
- 부수 섹션 제목은 내용에서 나온다("검토하다 발견한 e2e 결함 2건도 수리") — 고정 라벨이 아니다.
- **검증은 정확히 한 줄로 압축** — "단위 테스트 120개 · 타입체크 · e2e 12/12 전부 통과"처럼.
  기본 모드와 달리 여기서는 넣는다: 읽는 사람의 "안 깨졌나?"를 선제 차단하는 신뢰 장치다.
  단, 검사 종류별 나열·표로 늘리지 않는다.

### 문체 — 풀어 쓰는 개조식

종결은 명사형·"~음/~함/~둠"체를 유지하되, **문장은 완전하게** 쓴다. 압축의 대상은 어미지 정보가 아니다.

- **약어·내부 용어는 등장 즉시 괄호·동격으로 정의한다**: "알림 노출 규칙(정책)",
  "빈 껍데기 파일(shim)", "외부 무료 서비스(picsum.photos)".
- **메커니즘까지 잇는다**: "e2e가 죽음"에서 멈추지 말고 "상세 화면은 이미지 로딩까지 끝나야
  열리는데 그 이미지를 외부 서비스에서 받아옴 → 그 서비스 장애 = 화면이 안 열림 = 전 스위트
  사망"처럼 독자가 인과를 따라올 수 있게.
- **숫자로 말할 수 있는 것은 숫자로**: 순 −423줄, 전체 12개 전멸, 12/12 통과.
- **이전 PR·결정이 배경이면 번호로 연결한다**: "지난주 옮겼는데(#78), 그때 …을 남겨둠".
- **왜 그 선택을 했는가**: 대안이 있었으면 무엇을 왜 안 골랐는지 한 줄.

### 예시 (이 형태를 그대로 따른다)

```markdown
# 알림 노출 규칙 구조 정리 + e2e 안정화 (PR #85)

**배경**: 알림에는 "지금 상태 × 중요도 × 내 권한에 따라 어떤 버튼(확인·보관·삭제)을 보여줄지"
정하는 노출 규칙(정책)이 있음. 웹·모바일이 같은 규칙을 써야 해서 지난주 공유 패키지로
옮겼는데(#78), 그때 웹 화면 코드를 안 고치려고 옛 위치에 "실제 코드는 저쪽에 있어요"라고

### 여전히 넣지 않는 것

- 변경 파일 경로 목록. 파일은 그 자체가 판단을 설명할 때만 인용한다.
- 서문("정리했습니다")·맺음말·"다음 단계" 권유.
- 검증의 검사별 나열·표 — 한 줄로 압축(위 구조 참고).
- 3단계 이상 중첩. 최대 2단계(섹션 > 불릿).

## Common mistakes

| 실패 | 교정 |
|------|------|
| 항목을 내부 용어로 씀(캐시·쿼리키·리팩토링·경계) | 화면·버튼·기능 이름으로. 치환표를 거친다 |
| `fe`·`mobile` 같은 레포 약칭으로 묶음 | 사람들이 부르는 제품 이름으로 묶는다 |
| 커밋 제목을 그대로 붙여넣음 | 커밋 제목은 개발자에게 쓴 말이다. 다시 쓴다 |
| 무슨 화면인지 모르는 채 추측해서 씀 | 바뀐 파일 경로로 역추적하고, 그래도 모르면 묻는다 |
| 본문에 `(#66)` 번호를 섞음 | 맨 아래 `참조` 줄에 URL로 모은다 |
| 그날 만든 QA 리포트·아티팩트를 빠뜨림 | Artifact `list`로 확인한다. 화면 작업이면 거의 항상 있다 |
| 아티팩트 링크를 `참조` 줄로 내림 | `참조`는 아무도 안 누른다. 해당 항목 아래 `◦`로 붙인다 |
| 기본 출력에 `**볼드**`·`- ` 불릿·`#` 헤더를 씀 | 셀에서 문자 그대로 보임. 평문 + `•`·`◦` 만 쓴다 |
| 코드블록으로 안 감쌈 | 셀에 깔끔히 복사하도록 전체를 ``` 코드블록째 제시한다 |
| 날짜 헤더를 붙임 | 노션 행이 이미 날짜를 갖는다. 제품 이름으로 시작한다 |
| 항목마다 문제/조치/검증을 붙임 | 한 줄. 질문 받으면 그때 말한다 |
| 커밋을 그대로 나열 | PR/브랜치 단위로 합친다 |
| 머지된 커밋만 봄 | `--all`로 미머지 브랜치까지. 레포도 하나만 보지 않는다 |
| 검증 결과 나열 | 기본 모드는 뺀다. 자세히 모드는 마지막에 **한 줄**로만 |
| 줄표(`—`)로 항목과 효과를 이음 | AI 티가 난다. 쉼표·문장 분리·`◦` 한 줄로 바꾼다 |
| 블로커를 임의로 추가 | 이 스킬은 '오늘 한 일' 칸만 만든다. 요청받을 때만 쓴다 |
| 자세히 모드에서 서술형("~했다/~입니다")으로 씀 | 명사형·"~음/~함"체 종결 |
| 자세히 모드를 라벨 불릿(`증상:`·`조치:`)으로 채움 | 배경 → 이번 작업 → 검증 흐름. 예시 승인본을 따른다 |
