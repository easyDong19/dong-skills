# Explaining with Domain Context

## Overview

설명은 구조의 나열이 아니라 **이야기의 전달**이다. 독자는 이 저장소도, 도메인도, 대화의 맥락도 모른다고 가정한다 — 질문이 캐주얼해도("이거 설명해줘") 처음 인수인계받는 사람에게 말하듯 쓴다.

핵심 원칙: **독자가 각 조각을 이해하는 데 필요한 것을, 그 조각보다 먼저 준다.**

## 설명의 형태 (순서대로)

좋은 설명은 이 부분들로 이루어진다:

1. **문제와 도메인** — 이것이 다루는 현실 세계의 문제. 무엇이 없어서/불편해서 이게 존재하는가. 도메인 용어(업계 용어·프로젝트 고유 개념)는 **첫 등장에서 한 줄로 정의**한다. 예: "비계(공사장 외벽의 임시 작업 발판)", "candidate(AI가 PDF에서 뽑아낸 도면 이미지 후보)".
2. **큰 그림** — 전체 시스템에서 이 조각의 위치와 경계. 짝이 되는 컴포넌트, 상류·하류. 내부로 들어가기 전에 바깥부터.
3. **플로우 — 인과의 사슬로** — 각 단계를 "무엇을 한다"가 아니라 **"무엇이 이 단계를 촉발하고, 이 단계가 없으면 무엇이 무너지는가"**로 잇는다. 단계 번호는 붙여도 되지만, 번호 사이가 인과로 연결되어야 한다.
4. **의사결정과 기각된 대안** — 왜 이렇게 만들었는가. 코드 주석·커밋 메시지·설계 문서에서 발굴해서, 기각된 대안과 그 이유를 함께 적는다. "원래는 X였는데 Y 때문에 Z로 바꿨다"가 가장 가치 있는 정보다.
5. **함정과 제약** — 처음 보는 사람이 밟을 지뢰. 깨지기 쉬운 커플링, 문서화된 제약, "이거 고치면 안 됨".
6. **근거 링크** — 주장마다 파일 경로(`path:line`), 문서, 커밋, 이슈를 연결한다. 독자가 검증하고 더 파고들 수 있게.

표·다이어그램·요약은 **서사를 마친 뒤** 보조로 붙인다. 서사의 대체물이 아니다.

## 플로우 서술 규칙

```
❌ 나열: "1. 파일 업로드  2. Job 생성  3. 폴링  4. 완료"
✅ 인과: "선택한 페이지를 1장짜리 PDF로 분할해 올리면 서버가 추출 Job을
   만든다. 추출은 수 분이 걸리므로 응답을 기다리는 대신 Job id를 받아
   폴링한다 — Realtime이 주 경로고 폴링은 이벤트 유실 대비 안전망이다."
```

각 단계에서 자문: "독자가 '왜 이 단계가 필요하지?'라고 물으면 답이 이 문장 안에 있는가?"

## 시작 규칙

첫 문단은 **문제 또는 한 줄 본질**로 시작한다. 파일 목록·폴더 트리·"등장 인물" 표로 시작하지 않는다 — 그것들은 §2 큰 그림 이후에 온다.

## Common Mistakes

| 실수 | 교정 |
|---|---|
| 파일/구조 표부터 시작 | 문제·도메인 문단을 먼저, 구조는 그 다음 |
| 도메인 용어를 정의 없이 사용 | 첫 등장에서 괄호 한 줄 정의 |
| 단계 나열만 하고 "왜" 생략 | 단계마다 촉발 조건·존재 이유를 문장에 포함 |
| 의사결정 배경 생략 | 주석·커밋·문서에서 발굴해 기각된 대안과 함께 |
| 근거 없는 주장 | 파일:라인·문서·커밋 링크 연결 |
| 요약 표로 서사 대체 | 표는 서사 뒤 보조 자료 |
